**Context/Impact:**

* This project analyses Olympics Athletes’ (Ski/snowboard) performance recordings to produce several outputs for NBC broadcasts. Outputs include frame by frame numerical metrics such as rotation, angles, speed, tuck factor, as well as visual overlays such as 2D/3D skeletons, and cork ribbons.  
* To produce [ribbons](https://www.youtube.com/watch?v=cCcqEAXSMaM) that appear to float in space anchored to the athlete’s movement, the [LoFTR model](https://zju3dv.github.io/loftr/) is used to analyze the optical flow of the camera movement, by comparing features between two consecutive video frames, for every frame in the video.  
* LoFTR is containerized and deployed as a Vertex Endpoint \- [Code on GitLab](https://gitlab.com/google-cloud-ce/googlers/santoromike/mhformer/-/tree/feat/loftr/services/loftr?ref_type=heads).

* **Resource Efficiency** \- Calculated LoFTR’s GPU memory requirements, used `g2-standard-24` machine with 2 L4s; Configured gunicorn to automatically map different workers to each GPU, each with their own parallel threads to process data and feed the GPU to serve traffic. Monitored latency, requests and memory utilization dashboards in Vertex Endpoint for availability and responsiveness.  
* **Resource Efficiency \-** Debugged latency issues: The analysis client code was calling the end point using python request and google auth, without caching auth token and connection pooling; \>50% of the time was actually spent on input image encoding (b64), auth token refresh, and connection establishment. Fix: 1\) Use Vertex SDK which provides connection pooling and auth in session. 2\) Used Gemini to come up with a faster image encoding path (use jpeg instead of png). Result: \<100ms are now spent in those stages, instead of \~1s.
